## الوضع الحالي (ما ننطلق منه)

- المباراة الحالية ضد بوت فقط (`js/boxing-match.js`): أوامر `JAB/HOOK/UPPERCUT/SLIP/DODGE`
  من `COMMAND_POOL`، أمر كل 3 ثوانٍ، 60 ثانية، صحة 100/100، ضرر `DAMAGE`:
  `JAB 7، CROSS 9، HOOK 10، UPPERCUT 13، BODY 11`، `SLIP/DODGE 0`.
  `MoveValidator.feed(lm, nowMs)` يعيد `{status: 'valid'|'rejected', half}` — الحركة
  النصفية لا تُحسب. الانسحاب = خسارة. انتهاء الأمر بلا تنفيذ = ضرر timeout على اللاعب.
- الحسابات: Firestore `boxing_profiles`، الدخول باسم + كود (PIN لعبة، هاش SHA-256 ×1000
  + ملح، بلا Auth) — `js/boxing-firebase.js` (`normalizeName`، `registerCloud` بـ `ref.create()`،
  `loginCloud`، `syncCloud` مع التحقق من كود الجلسة، `listProfiles` للترتيب).
- ELO: `K=32`، يبدأ من 1000، `recordMatch` (فوز +50 XP، تعادل +25، خسارة +10، وكل
  إصابة ناجحة +5 XP) — `js/boxing-profile.js`، وصيغة المستوى `xpForLevel = 100·L·(L−1)/2`.
- الأفاتار: `window.HalbaBoxingAvatar` في `js/boxing-avatar.js` — `init/setLevel/togglePushup/
  toggleHoodie/setVisible/isReady`، دورة ضغط إجرائية، عضلات حسب المستوى. **حالياً مثيل
  واحد** (الرئيسية) — يحتاج إعادة صياغة صغيرة كمصنع ليعمل مثيل ثانٍ للخصم (قسم 5).
- القواعد الحالية (`firestore.rules`): قراءة مفتوحة، إنشاء بتحقق من الحقول، تحديث يجمّد
  `codeHash/salt/createdAt/name`، حذف ممنوع. ELO بين 100 و3000، المستوى 1–100.

## 1. الغرف — مجموعة `challenge_rooms`

مستند واحد لكل تحدي. المعرّف: **كود غرفة من 6 أحرف** (`A-Z0-9`، يولّده المضيف عشوائياً)
— يُستعمل أيضاً كطريقة انضمام بديلة (قسم 2).

```js
challenge_rooms/{roomId} = {
  host: string,            // الاسم بعد التطبيع (normalizeName) — صاحب الدعوة
  guest: string,           // الاسم بعد التطبيع — المدعو (فارغ '' حتى يقبل أحد بالكود)
  hostDisplay: string, guestDisplay: string,
  hostElo: int, guestElo: int,       // لحساب ELO عند النهاية (كل عميل يحسب بنفسه)
  hostLevel: int, guestLevel: int,   // لعضلات أفاتار الخصم
  status: 'waiting' | 'ready' | 'fighting' | 'finished' | 'cancelled',
  seed: int,               // بذرة جدول الأوامر المشترك (قسم 3)
  durationMs: 60000,
  createdAt: serverTimestamp,
  acceptedAt: serverTimestamp | null,  // لحظة قبول الضيف — مرساة العد التنازلي
  startsAt: int | null,    // ms epoch، يحسبه العميلان من acceptedAt + 5000
  a: { hits: int, dodges: int, misses: int, hp: int,
       lastSeen: serverTimestamp,      // نبضة كل 5 ثوانٍ
       finish: null | { result, hpSelf, hpOpp, hits, at } },
  b: { /* نفس حقول a — للاعب الثاني */ },
  winner: string | null,   // الاسم المطبّع للفائز، أو 'draw'، أو 'disputed'
  forfeitBy: string | null,
  updatedAt: serverTimestamp
}
// أحداث موثّقة — مجموعة فرعية (لا مصفوفة في المستند: تتجاوز حدود الحجم وتتصادم كتاباتها)
challenge_rooms/{roomId}/events/{seq} = {
  seq: int,                // 1، 2، 3… لكل لاعب على حدة (a-1, a-2… أو رقم + player)
  player: 'a' | 'b',
  kind: 'hit' | 'dodge' | 'miss' | 'forfeit',
  move: string | null,     // من COMMAND_POOL + CROSS/BODY
  dmg: int,                // من جدول DAMAGE — 0 للتفادي والخطأ
  slot: int,               // رقم الأمر في الجدول (للتحقق: الحركة = أمر تلك اللحظة)
  at: serverTimestamp,     // ترتيب الأحداث عند الطرفين
  atClient: int            // ms من ساعة الكاتب (لتشخيص الفارق فقط، لا للحسم)
}
```

- **الحالات:** `waiting` (ينتظر قبولاً) ← `ready` (قَبِل الضيف) ← `fighting` (بدأ العدّ)
  ← `finished` (انتهى/انسحاب/انقطاع). `cancelled` من `waiting` فقط (رفض الدعوة أو انتهاء
  مهلة 5 دقائق بلا قبول). `finished` نهائية — لا كتابة بعدها إلا `finish` الطرف الثاني
  (يُسمح به 10 ثوانٍ بعد الأول، ثم تُقفل).
- **من هو a ومن هو b؟** المضيف = `a`، الضيف = `b` دائماً — يحدَّد عند الإنشاء، فلا
  التباس في الأحداث والعدّادات.

## 2. تدفق التحدي خطوة بخطوة

1. **الدعوة — طريقتان (v1):**
   - **(أ) بالاسم (الأساسية):** من صف الترتيب أو من الملف: زر «تحدَّ» بجانب أي لاعب.
     ينشئ المضيف غرفة (`status: 'waiting'`، `guest` = اسم المدعو المطبّع، `seed` عشوائي).
     المدعو — إن كان فاتحاً الصفحة — يرى الدعوة فوراً عبر استماع حي (قسم 3):
     استعلام `challenge_rooms where guest == اسمي, status == 'waiting'` مع `onSnapshot`
     → بطاقة «تحدّاك فلان — اقبل / ارفض».
   - **(ب) بكود الغرفة (بديل):** المضيف يرى كوداً من 6 أحرف ويرسله للخصم (واتساب/مكالمة).
     الضيف يكتب الكود في «ادخل كود غرفة» → يقرأ المستند → إن كان `waiting` و`guest` فارغاً
     أو يساويه، يضع نفسه `guest` ويقبل. **بلا غرف عامة مفتوحة في v1** (تجنّباً للانتظار
     والغرباء) — قرار للمالك (قسم 9).
   - **الرفض:** الضيف يضغط «ارفض» → `status: 'cancelled'`، وتختفي الدعوة عند المضيف.
     **مهلة:** غرفة `waiting` تُتجاهل بعد 5 دقائق (العملاء يصفّون بالـ `createdAt`)؛
     بلا Functions لا يوجد حذف تلقائي — الغرف القديمة تبقى كأرشيف.
2. **القبول ← الجاهزية:** الضيف يقبل → `status: 'ready'` + `acceptedAt: serverTimestamp`.
   كل عميل يحسب `startsAt = acceptedAt + 5000` ويعرض عدّاً تنازلياً 5…4…3…2…1.
   (مرساة خادم واحدة، لا ساعة كل هاتف — الفارق بين الهاتفين يبقى ~زمن الشبكة فقط.)
3. **القتال (60 ثانية):** عند `startsAt` يبدأ الجدول المشترك (قسم 3): أمر كل 3 ثوانٍ،
   **نفس الأمر للاعبين في نفس اللحظة** — من ينفّذه موثّقاً أولاً يسجّل إصابة.
   كل عميل يتحقق من حركاته هو بالكاميرا (`MoveValidator` نفسه) ويكتب أحداثه هو فقط.
   الصحة والعدّادات تُحسب محلياً عند الطرفين من نفس سجل الأحداث (قسم 3).
   أفاتار الخصم تحت الكاميرا يقوم بالحركة التي نفّذها الخصم (قسم 5).
4. **النهاية:** KO (صحة ≤ 0) أو انتهاء الـ 60 ثانية. كل عميل يحسب النتيجة من سجل
   الأحداث ويكتب `finish` في جانبه (`a.finish` / `b.finish`). النتيجة المعتمدة:
   `finish` الطرفين متطابقتان → `winner` + `status: 'finished'`. مختلفتان → `disputed`
   (قسم 4). ثم كل عميل يحدّث ملفه محلياً بـ `Profile.recordMatch` (نفس دالة مباراة
   البوت: ELO + XP) ويزامن عبر `syncCloud` — **إلا في حالة `disputed`: لا مزامنة ELO**.
5. **إعادة المباراة:** زر «تحدٍّ جديد» ينشئ غرفة جديدة بنفس الخصم (بذرة جديدة) —
   بلا زر إعادة داخل نفس الغرفة (الغرفة المنتهية أرشيف).

## 3. المزامنة الحية — ماذا يُرسل، وكم مرة، وبأي زمن

- **ما يُرسل كل لاعب (فقط):** أحداثه هو — `hit` عند كل حركة موثّقة صحيحة، `dodge`
  عند كل انزلاق/تفادٍ موثّق، `miss` عند انتهاء أمر بلا تنفيذ، `forfeit` عند الانسحاب —
  + نبضة `lastSeen` كل 5 ثوانٍ على جانبه في مستند الغرفة. **لا نقاط كاميرا ولا فيديو
  ولا صحة مباشرة** — الصحة تُشتقّ، لا تُرسَل (حتى لا يكتب لاعب «صحتي 100» كذباً).
- **الكمية:** مباراة 60 ثانية ≈ 20 أمراً → ~20 حدثاً لكل لاعب كحد أقصى + 12 نبضة
  + 2–3 كتابات حالة = **~35 كتابة لكل لاعب في المباراة**. القراءات: استماع `onSnapshot`
  على مستند الغرفة (تغيير واحد لكل كتابة خصم) + استماع على مجموعة `events` (وثيقة
  جديدة لكل حدث خصم) ≈ **~40 قراءة لكل لاعب**. 100 مباراة في اليوم ≈ 7,500 عملية —
  **ضمن الحد المجاني** (Spark: ~50 ألف قراءة و20 ألف كتابة يومياً). الغرف المنتهية
  تُفصَل عنها المستمعات فوراً (بلا استماع دائم على كل الغرف).
- **الاستماع:** `onSnapshot` على مستند الغرفة (الحالة + عدّادات الجانب الآخر + `finish`)
  + استعلام `events orderBy('at')` مع حدّ للوثائق الجديدة فقط. **لا polling.**
- **الزمن المتوقع:** Firestore `onSnapshot` عادة 100–500ms على اتصال جيد. اللعبة
  تتحمّل هذا لأن الإيقاع 3 ثوانٍ لكل أمر — الحدث يصل قبل الأمر التالي. **لا مزامنة
  إطار بإطار** (مستحيل وغير لازم: الكاميرا محلية، والأفاتار يُقاد بالأحداث).
- **جدول الأوامر المشترك (قلب التصميم):** بذرة `seed` في الغرفة + مولّد أرقام حتمي
  (`mulberry32(seed)`) + `COMMAND_POOL` نفسه → الأمر رقم `k` يبدأ في
  `startsAt + k·3000` وهو نفسه عند الطرفين، **بلا أي كتابة إضافية**. مباراة البوت
  الحالية تستعمل `Math.random` — نسخة الأونلاين تستبدله بالمولّد المزروعة (نفس
  `COMMAND_POOL` ونفس مهلة 3 ثوانٍ).
- **حساب الصحة من السجل (عند الطرفين، بنفس القاعدة):**
  `HP = 100 − Σ ضرر إصابات الخصم غير المُلغاة`. الإصابة تُلغى إن كتب المدافع حدث
  `dodge` خلال 1500ms قبل `at` الإصابة. إصابة لا تطابق أمر لحظتها (`move != أمر الـ slot`
  أو `slot` خارج الوقت) **تُتجاهل** عند الحساب — هكذا لا تنفع الأحداث المزوّرة حتى
  إن كُتبت. KO عند `HP ≤ 0`. التعادل عند تساوي الصحة في نهاية الوقت.

## 4. منع الغش في اللعب الحي — بصراحة

- **ما يبقى كما في مباراة البوت:** كل عميل يتحقق من حركاته هو بالكاميرا؛ الحركة
  النصفية لا تُحسب؛ المحاكاة (`trySimulatedMove` / لوحة المفاتيح) **تُمنع تماماً في
  مباراة أونلاين** (زراها لا يظهران؛ `trySimulatedMove` يرفض إن كانت المباراة أونلاين)
  — وإلا كان الفوز بلوحة مفاتيح.
- **ماذا يرى الخصم:** العدّادات + الصحة المشتقة + حركة الأفاتار فقط. لا يرى كاميرتك
  ولا نقاطك — فلا يستطيع التشكيك في حركتك ولا تقليدها لحظياً.
- **ماذا يستطيع عميل عدائي أن يزوّر (بلا خادم وبلا Auth — وهذا هو الحد الحقيقي):**
  - يكتب أحداث `hit` وهمية باسمه → لكن العميل النزيه **يتجاهلها** عند الحساب إن
    خالفت الجدول (قسم 3)، فيحسب نتيجة مختلفة عن نتيجة المزوّر → **`disputed`**،
    وبلا مزامنة ELO. التزوير إذن **لا يمنح ELO**، لكنه يفسد المباراة (تظهر «متنازَع
    عليها» بدل فوز واضح).
  - يكتب أحداثاً باسم خصمه (الـ `player` حقل عادي) → القواعد بلا Auth **لا تستطيع
    منع ذلك** (لا تعرف من الكاتب). التخفيف: كل حدث يُقبل فقط إن كان `player` هو
    صاحب الجانب الذي كتبه… وهذا أيضاً لا يُتحقق منه بلا Auth. الاعتماد هنا على
    التقاطع: النتيجتان المختلفتان → `disputed`.
  - يرفع ELO ملفه مباشرة عبر API (ممكن أصلاً اليوم في `boxing_profiles` — موثّق
    في القواعد الحالية) → خارج نطاق مباراة الأونلاين؛ لا يمسّ نتيجة مباراة بعينها.
  - يفتح غرفاً وهمية ويرسل دعوات مزعجة → التخفيف: غرفة واحدة `waiting` لكل مضيف
    (العميل يرفض إنشاء الثانية قبل إغلاق الأولى) + مهلة 5 دقائق + زر حظر بسيط
    (قائمة محظورين محلية في `localStorage` — قرار للمالك).
- **الحل الحقيقي (لاحقاً، ليس v1):** Firebase Auth (كل لاعب بهوية) + Cloud
  Functions (دالة تحسم النتيجة من السجل وتكتب ELO — العميل لا يكتب ELO أبداً).
  هذا يحتاج **خطة Blaze (مدفوعة حسب الاستعمال)** + قرار المالك. حتى ذلك الحين،
  مباريات الأونلاين **«تجريبية — الثقة بين اللاعبين»**، وتُعرض كذلك في الواجهة.

## 5. أفاتار الخصم تحت الكاميرا

- **الموضع:** في لوحة المباراة، **تحت نافذة كاميرا اللاعب** (كما طلب المالك) —
  مسرح صغير بنفس نمط الرئيسية (منصة نيون)، بارتفاع ~260px على الهاتف.
- **إعادة الاستعمال:** `js/boxing-avatar.js` الحالي مثيل واحد (`window.HalbaBoxingAvatar`).
  للخصم نحتاج **مثيلاً ثانياً مستقلاً**: إعادة صياغة صغيرة — مصنع
  `createAvatarViewer(stageEl)` يعيد `{ init, setLevel, setVisible, isReady,
  playMove(move), setPushup(on) }`؛ الرئيسية تستعمل مثيلاً، والمباراة مثيلاً للخصم.
  المستوى من `guestLevel/hostLevel` في الغرفة (عضلات الخصم تعكس مستواه الحقيقي).
- **القيادة بالأحداث الحية:** عند وصول حدث خصم (`onSnapshot` على `events`):
  - `hit` بحركة `JAB/CROSS/HOOK/UPPERCUT/BODY` → الأفاتار ينفّذ اللكمة نفسها
    (حركات إجرائية قصيرة 0.6–0.9 ثانية على العظام — امتداد لنظام الضغط الإجرائي
    الحالي: الكتف والمرفق والجذع؛ `SLIP/DODGE` → انحناءة تفادٍ جانبية).
  - `dodge` → حركة تفادٍ؛ `miss` → لا شيء (أو هزة رأس خفيفة — قرار صغير للباني).
  - بين الأحداث: وقفة هادئة (نفس `applyIdlePose` في الرئيسية) + تنفّس خفيف.
  - أثناء العد التنازلي وقبل البدء: **دورة الضغط** (`setPushup(true)`) — الأفاتار
    «يُحمي» بتمرين الضغط، كما طلب المالك أصلاً (الخصم يُرى وهو يتمرّن).
- **ملاحظة:** أفاتار الخصم يمثّل **حركات موثّقة فقط** — إن لم ينفّذ الخصم شيئاً،
  أفاتاره واقف هادئ. هذا هو الضمان البصري: ما تراه هو ما تحققت منه كاميرا الخصم.

## 6. المؤقت المتزامن، الانسحاب، انقطاع الاتصال

- **المؤقت:** `startsAt = acceptedAt + 5000` (مرساة خادم). كل عميل يحسب
  `timeLeft = startsAt + 60000 − Date.now()` محلياً ويعرضه؛ فارق الساعات بين
  الهاتفين (~ثانية) مقبول لأن الحسم ليس بالوقت المعروض بل **بسجل الأحداث**:
  أي حدث بعد `startsAt + 60000` يُتجاهل عند الحساب.
- **الانسحاب الصريح:** زر «انسحاب» → يكتب `forfeit` + `finish{result:'loss'}`
  و`forfeitBy` → خسارة فوراً للمنسحب (نفس قاعدة مباراة البوت)، وفوز للطرف الآخر،
  وتُزامَن ELO كالمعتاد.
- **انقطاع الاتصال:** نبضة `lastSeen` كل 5 ثوانٍ على جانب كل لاعب. إن تجاوز عمر
  نبضة الخصم **15 ثانية** أثناء القتال: تظهر «الخصم غير متصل — ننتظر 10 ثوانٍ».
  عاد قبل انتهاء المهلة → تكمل المباراة (الحالة كلها في Firestore، فالعودة ممكنة
  من نفس الغرفة). لم يعد → تنتهي المباراة بفوز اللاعب الحاضر، وتُكتب
  `winner` + `finish` للطرفين (الحاضر يكتب عن نفسه فوزاً؛ الغائب يبقى بلا `finish`
  وتُحسم النتيجة من الجانب الواحد بعد مهلة 10 ثوانٍ إضافية).
- **إغلاق الصفحة/الانهيار:** يُعامَل كانقطاع (لا `forfeit` صريح) — نفس المهلة
  والفوز للحاضر. لا عقوبة إضافية على المنقطع غير خسارة المباراة.

## 7. قواعد Firestore الإضافية

تُضاف إلى `firestore.rules` (تُنشر من الكونسول — CLI القواعد يفشل 403 كما هو معروف):

```rules
match /challenge_rooms/{roomId} {
  function validRoom(d) {
    return d.keys().hasOnly(['host','guest','hostDisplay','guestDisplay',
          'hostElo','guestElo','hostLevel','guestLevel','status','seed',
          'durationMs','createdAt','acceptedAt','startsAt',
          'a','b','winner','forfeitBy','updatedAt'])
      && d.host is string && d.host.size() >= 2 && d.host.size() <= 30
      && d.guest is string && d.guest.size() <= 30
      && d.status in ['waiting','ready','fighting','finished','cancelled']
      && d.hostElo is int && d.hostElo >= 100 && d.hostElo <= 3000
      && d.guestElo is int && d.guestElo >= 100 && d.guestElo <= 3000
      && d.durationMs == 60000
      && d.a.hp is int && d.a.hp >= 0 && d.a.hp <= 100
      && d.b.hp is int && d.b.hp >= 0 && d.b.hp <= 100
      && d.a.hits is int && d.a.hits >= 0 && d.a.hits <= 25
      && d.b.hits is int && d.b.hits >= 0 && d.b.hits <= 25;
  }
  function forwardOnly(oldS, newS) {
    return (oldS == 'waiting'    && newS in ['ready','cancelled'])
        || (oldS == 'ready'      && newS in ['fighting','cancelled'])
        || (oldS == 'fighting'   && newS in ['finished'])
        || (oldS == newS); // تحديث عدّادات/نبضات بلا تغيير حالة
  }
  allow read: if true;
  allow create: if validRoom(request.resource.data)
    && request.resource.data.status == 'waiting'
    && request.resource.data.winner == null
    && request.resource.data.a.finish == null
    && request.resource.data.b.finish == null;
  allow update: if validRoom(request.resource.data)
    && forwardOnly(resource.data.status, request.resource.data.status)
    && request.resource.data.host == resource.data.host
    && request.resource.data.guest == resource.data.guest
    && request.resource.data.seed == resource.data.seed
    && request.resource.data.createdAt == resource.data.createdAt
    && (resource.data.status != 'finished'
        || request.resource.data.status == 'finished'); // المنتهية لا تعود
  allow delete: if false;

  match /events/{seq} {
    function validEvent(d) {
      return d.keys().hasOnly(['seq','player','kind','move','dmg','slot','at','atClient'])
        && d.player in ['a','b']
        && d.kind in ['hit','dodge','miss','forfeit']
        && d.move in ['JAB','CROSS','HOOK','UPPERCUT','BODY','SLIP','DODGE', null]
        && d.dmg is int && d.dmg >= 0 && d.dmg <= 13
        && d.seq is int && d.seq >= 1 && d.seq <= 25;
    }
    allow read: if true;
    allow create: if validEvent(request.resource.data)
      && request.resource.data.at == request.time; // ختم الخادم — لا تواريخ مزوّرة
    allow update, delete: if false; // الأحداث سجلّ لا يُعدَّل
  }
}
```

- **ما لا تستطيع القواعد فعله بلا Auth (يُقال صراحة):** منع لاعب من الكتابة في جانب
  خصمه؛ عدّ أحداث المجموعة الفرعية؛ فرض «غرفة واحدة لكل مضيف». هذه تُضبط
  بالعميل + بالتقاطع (قسم 4) حتى يجي Auth.
- **فهرس:** استعلام الدعوات (`guest == X, status == 'waiting'`) حقل واحد + حقل
  واحد — بلا فهرس مركّب. إن أُضيف فلتر `createdAt` فسيطلب Firestore فهرساً مركّباً
  (يُنشأ من رابط خطأ الكونسول عند أول تشغيل).

## 8. خطة الاختبار

1. **متصفحان headless (الأساس — نفس نمط `/tmp/pw` و`/tmp/home-check`):**
   Playwright + اعتراض CDN محلياً + خادم محلي. حسابان جديدان (`اختبار-أ` /
   `اختبار-ب` عبر `registerCloud`، ويُحذفان بعد الاختبار):
   - إنشاء غرفة من أ → تظهر الدعوة عند ب → قبول → عدّ تنازلي → قتال 60 ثانية
     بحركات **محاكاة** (`trySimulatedMove` — مسموحة في الاختبار، ممنوعة في اللعب الحي).
   - التحقق: عدّادات الطرفين متطابقة، الصحة المشتقة متطابقة عند الطرفين،
     ELO يتغير بالمقدار الصحيح عند الطرفين (`K=32` ضد ELO الخصم)، و`winner`
     في الغرفة صحيح.
2. **قطع الاتصال:** إغلاق متصفح ب منتصف القتال → مهلة 15ث + 10ث → فوز أ،
   و`winner` صحيح، وبلا تعليق.
3. **انسحاب:** زر انسحاب عند أ → خسارة أ فوراً، وفوز ب، وELO يُزامَن.
4. **تزوير:** عميل ثالث يكتب حدث `hit` وهمياً (خارج الجدول) → العميلان النزيهان
   يتجاهلانه، والنتيجة `disputed` وبلا مزامنة ELO.
5. **زمن:** قياس تأخر وصول الحدث (من كتابة أ إلى ظهوره عند ب) على اتصال عادي —
   الهدف < 1 ثانية في 95% من الأحداث.
6. **اختبار حي على الهاتف (القبول النهائي):** مجيد وعبد المجيد — هاتفان حقيقيان،
   تحدي حقيقي بالكاميرا (وليس محاكاة)، 60 ثانية كاملة، ثم التحقق من: العدّادات،
   الصحة، ELO، أفاتار الخصم يقوم بالحركات، وبلا تعليق. **هذا هو اختبار «الموسَيان
   يلعبان ضد بعضهما» الذي طلبه مجيد.**
7. **حسابات اختبار:** تُحذف مستنداتها من `boxing_profiles` ومن `challenge_rooms`
   بعد كل جولة اختبار (الغرف المنتهية تُترك 24 ساعة ثم تُحذف يدوياً من الكونسول
   حتى يجي تنظيف تلقائي).

## 9. التقسيم والترتيب

**ما يُبنى أولاً — جهة الملاكمة (عندنا):**
1. `js/boxing-challenge.js` (جديد): إنشاء/قبول/رفض الغرف، الاستماع الحي، جدول
   الأوامر المزروع، كتابة الأحداث، حساب الصحة من السجل، النبضة، الانسحاب،
   الانقطاع، `finish` + التقاطع (`disputed`).
2. واجهة في لوحة المباراة: قسم «تحدٍّ أونلاين» (تحدَّ من الترتيب / أدخل كود غرفة /
   الدعوات الواردة / العد التنازلي / نتيجة المباراة + زر تحدٍّ جديد).
3. مصنع الأفاتار (`createAvatarViewer`) + مسرح الخصم تحت الكاميرا + حركات
   اللكمات الإجرائية (`playMove`) + دورة الضغط أثناء العد التنازلي.
4. منع المحاكاة ولوحة المفاتيح في مباراة الأونلاين.
5. القواعد (قسم 7) + خطة الاختبار (قسم 8).

**ما ينتظر موسى عبد المجيد (القلب):**
- نقطة دخول «تحدٍّ» في واجهة التطبيق الرئيسية (تفتح الملاكمة على خصم محدد
  مسبقاً — رابط عميق أو تمرير اسم الخصم)؛ وقرار: هل يظهر زر «تحدَّ» في الملف
  الرئيسي للقلب أيضاً أم في الملاكمة فقط؟
- لاحقاً (ليس v1): إشعارات push للضيف الغائب (FCM)، وحضور/تواجد (من متصل الآن)،
  وmatchmaking عام، وFirebase Auth + Cloud Functions للحسم الموثوق.

**قرارات تحتاج صاحب اللعبة (عبد المجيد — ويوافق عليها مجيد):**
1. **الدعوة بالاسم مباشرة أم غرف عامة أم كود؟** التوصية: بالاسم + كود كبديل،
   بلا غرف عامة في v1.
2. **التحدي مصنّف (ELO) أم ودي (بلا ELO) أم الاثنان؟** التوصية: مصنّف افتراضياً
   مع خيار ودي عند إنشاء التحدي — لأن ELO روح اللعبة، لكن التزوير أسهل في المصنف.
3. **هل نطلق v1 «تجريبياً» بثقة محدودة، أم ننتظر Auth + Functions (Blaze)؟**
   التوصية: إطلاق v1 تجريبياً بين الأصدقاء أولاً (مجيد وعبد المجيد ومن يعرفونهما)،
   والانتقال إلى Auth + Functions قبل أي إعلان عام.
4. (إضافي) **عقوبة انتهاء الأمر في PvP؟** في مباراة البوت: ضرر timeout على
   اللاعب. في PvP التوصية: **بلا عقوبة في v1** (الخطأ يكفي أنه يضيّع فرصة إصابة)
   — تُراجَع بعد أول اختبار حي.
5. (إضافي) **هل يرى كل لاعب أمر الخصم الحالي؟** نعم حتماً (نفس الجدول) — وإلا
   لا معنى للتفادي. التوصية: إظهار أمر الخصم بجانب أمرك («الخصم: هوك») حتى
   يعرف اللاعب متى يتفادى.
